# Workflow invocation harness

This optional Rust harness preserves a bounded optimization assignment across
agent calls, records cumulative execution evidence, and returns every worker
result to its coordinator for adoption. It complements the Skills; it does not
replace their professional judgment, permission boundaries, or project records.

The [normal adapter entries](adapters/README.md) also provide controlled direction
delivery, a cooperative HTTP sender, and source-to-managed correction recovery.
These local repairs cover only their selected receivers. The Hook, direct shell
calls and existing live tasks do not gain those guarantees by installation.

The core is host-neutral. The checked-in project Hook is a Codex adapter only.
This release intentionally provides no Hook configuration or compatibility
shim for Claude Code, Cursor, or other agent hosts.

## Optional Codex owner adapter

The [owner adapter](adapters/README.md) connects professional choices to an
ordinary Batch and its actual configuration consumer. It prepares the selected
problem and resource descriptions, delivers authorized material through an
explicit Codex call, and saves the returned choice for adoption and recovery.
The Batch checks that the receiving operation uses the adopted effective inputs.

The [Batch interface](../../skills/frontier-optimization/references/batch-current.md#professional-realization-and-actual-input-use)
owns the choice. Preparation alone does not prove model delivery, and delivery
or matching inputs do not prove professional adequacy. An unchanged applicable
choice can be reused; an uncertain call is not automatically repeated. The
adapter requires an installed Codex binary and host-selected model, effort, call
allowance and timeout. It adds no Skill installation or routine reviewer.

This adapter is separate from the Codex Hook and the managed subprocess host.
The local tests use substituted transports and exercise configuration consumption
and recovery. The source installation's behavioral observations and project logs
are outside this portable bundle. Neither those records nor the release checks
establish adoption or improved outcomes in another project.

## What it controls

Protocol version 2 is enabled when a task includes a `research` object. It can:

- deliver the configured investment policy location so participating requests
  and independent checks can resolve its relative reference links;
- deliver a research question, missing observation, current rationale, sources,
  constraints, alternatives, and role-specific methods;
- preserve the whole-chain advantage hypothesis, decisive prospective
  conditions, and selected target feedback across owner and Batch handoffs;
- bind a consequential decision to its adopted objective, evaluation, and
  current-work sources, including an explicit feedback-timing disposition;
- carry validated current-use corrections into Worker preparation, reject stale
  queued work, and retire active invocations on the managed subprocess path;
- keep reusable understanding, source bytes, and accepted returns once, then
  provide exact retrieval locators instead of repeating the complete history;
- keep a broader controlling objective separate from a local assignment and
  bind optional current-use coverage to the exact saved objects a request uses;
- retain delayed observations, delivery failures, capability limitations, and
  recoverable alternatives without converting them into automatic support work;
- correlate a worker return with the invocation that created it;
- retain cumulative elapsed time, model tokens, compute, and currency-specific
  spending without treating unknown values as zero;
- withhold continuation at a selected return boundary, changed source, pause,
  unresolved effect, or material challenge; and
- recover persisted state without blindly repeating an uncertain call.

The harness does not sandbox an uncooperative process, settle external effects,
prove that a result is correct, or intercept host tools that are not connected
to one of its adapters.

[Consequential-meaning audits](../../skills/frontier-optimization/references/worker-interfaces.md#audit-consequential-meaning)
reuse existing owners and selected independent questions. Source identity does
not establish user or environmental authority; consistent summaries can share
one wrong premise. Validate the actual configuration, action or terminal claim
on the entry exercised. Native reminders and observed creation/follow-up inputs
do not certify direct commands, other steering, nested calls or every live
worker. This adds no runtime gate or universal semantic checker.

Implementation conditions use the existing [technical owner guidance](../../skills/frontier-optimization/references/technical-design.md#design-consequential-parameter-choices).
The [practice cases](tests/implementation-practice-cases.md) and
[verification record](tests/implementation-practice-results.md) distinguish ordinary
executor behavior, project result-source checks and unverified research benefit.
No new runtime gate or per-parameter model call is introduced. Rule deployment
does not update an existing worker's plan; inspect its next affected use through
the current owner and report only execution paths actually exercised.

Professional engineering guidance is selected through the existing
[technical owner rules](../../skills/frontier-optimization/references/technical-design.md#apply-professional-engineering-knowledge)
and [knowledge reuse entry](../../skills/frontier-optimization/references/batch-current.md#reuse-working-knowledge).
Deliver receiver-readable instructions and material applicability conditions;
catalog metadata, available files and verified delivery are not actual adoption.
Use the host's existing file or Skill access where available. The repository
reference helper accepts repository sources, not arbitrary user-level Skill
paths. A different supported reading path or necessary supplied content can
resolve access without changing that boundary or installing a Skill.
[Installation requires user confirmation](../../skills/frontier-optimization/references/user-decisions.md#skill-installation).
No new semantic validator, runtime gate or cross-platform interception is added.

Evaluation work uses [professional preparation and reuse](../../skills/frame-optimization/references/measurement-design.md#professional-preparation-and-reuse)
in ordinary Batch work, formal design, adoption and recovery. Unchanged inputs
and a passing prior judgment do not establish fitness for cumulative or changed
use. Selected independent audits can examine inherited premises and omitted
needs; the existing owner handles correction through the actual receiving path.
The [evaluation repair record](tests/evaluation-design-results.md) separates
source and link checks, bounded behavior samples, and live-project adoption.
The runtime has not gained the ability to detect unknown professional omissions
or certify an owner's judgment. Codex Hook coverage remains limited to its
connected events; source deployment does not update every running worker.

## Agent capacity and coverage

The shared [Agent capacity and continuation rules](../../skills/frontier-optimization/references/worker-interfaces.md#agent-capacity-and-continuation)
apply to first delegation, nested work, follow-up and recovery. The existing
owner selects useful work and preserves necessary independence. The host
adaptation supplies its actual dispatch, lookup, context and release behavior.
This optional Harness preserves participating invocation state; it does not
allocate a global agent pool or impose a cross-platform thread limit.

Unknown capacity permits a normal authorized attempt when the same work has no
unresolved dispatch. Unknown startup does not permit repetition. A successful
capacity query is not a reservation. Use a credible availability change or host
retry signal before retrying a confirmed refusal; do not infer release from
completion, interruption or elapsed time. Waiting parents that occupy every
place needed by their children must safely hand saved work to an existing owner
for serial execution, use a supported yield/resume mechanism, or report the
exact unavailable capability. The Harness cannot create that host capability.

| Entry | Implemented protection | Limit |
| --- | --- | --- |
| Controlled adapter | Durable invocation state and correlated recovery | Adapter receipts must describe actual backend evidence; declarations alone do not prove it |
| Participating native host bridge | Per-run dispatch association and return binding | The caller must use the bridge and preserve a lookup association for the real host call |
| Legacy native bind after dispatch | Associates an available handle with a pending invocation | No pre-dispatch association; a lost response requires the host's original records |
| Codex Hook | Checks or observes its supported registered events | Codex only; skipped or unmapped children, unsupported calls and unregistered sessions are not covered |
| Direct calls and other platforms | Shared owner rules | No automatic interception or global lifecycle enforcement is claimed |

Maintain only the consequential capabilities of an execution entry actually in
use. No Claude Code or Cursor adapter, universal close operation, fixed reserve,
per-dispatch approval or capacity registry is supplied by this change. Existing
task records retain failed attempts, usage and unresolved effects; result
adoption remains separate from whether an agent can be reused or released.

The [capacity cases](tests/agent-capacity-cases.md) define the audit problems and
behavioral controls. The [verification record](tests/agent-capacity-results.md)
separates mechanical recovery checks, executor behavior and unverified live
research benefit.

Current-use checks verify retained finding identity, saved source bytes, and the
request consumed by a cooperating host. They do not decide whether a correction
is semantically sound. The existing owner must first validate and adopt the
corrected work with the Skill helper; direct or unsupported dispatch paths still
require that owner to inspect the actual outgoing task.

## Reusable context and exact delivery

The Python resolver path uses `frontier_references.py resolver --output` to
prepare a `.delivery.json` sidecar. Run `deliver --repo WORKSPACE --path SIDECAR`
at consumption and send its complete stdout. The request preserves current role
guidance, selected objective/evaluation/work, explicit assignment, original
evidence, feedback timing and return obligations. A raw export remains diagnostic.
Both `verify-delivery` and `deliver` check the current governing basis, including
new unbound requests; a prior verification does not replace the send-time check.
An affected stale request is refused before operative output. Reconcile through
the existing owner and prepare again. Historical evidence retains its selected
snapshot, and a policy release alone does not invalidate scientific observations.
These checks do not control later unmediated calls or guarantee sound judgment.

The coordinator can retain one current explanation in `update.context` and name
the invocations whose returns it incorporates. When a later return does not
change that explanation, `context_unchanged` records the reuse without creating
another summary. Unadopted returns remain available as evidence.

The harness stores selected source and return bytes as shared SHA-256-addressed
evidence. A prepared request includes verified retrieval instructions. A
participating host can retrieve only the needed value with:

```sh
tools/workflow-harness/target/release/workflow-harness \
  host context-read RUN_DIRECTORY SNAPSHOT_SHA256 /by_invocation/INVOCATION_ID
```

Other supported selectors include `/full_sources/0`, `/current_use`, and JSON
pointers below a selected return. Before sending a prepared request, a
cooperating host can run `host context-check RUN_DIRECTORY REQUEST.json` to
verify its delivery identity and scoped source state. These checks establish
which bytes were delivered; they do not establish their truth, relevance, or
authority, and an opaque remote host must provide equivalent access before
claiming coverage.

The native context is a concise reminder, not a forecasting engine or decision
maker. The existing owner still decides whether target feedback is ready,
whether a delay is necessary, and how external changes or intervention-induced
effects alter the next commitment. Behavioral examples live in
[`tests/target-feedback-cases.md`](./tests/target-feedback-cases.md) and
[`tests/foresight-cases.md`](./tests/foresight-cases.md). Additional bounded
cases cover [capability learning](./tests/capability-learning-cases.md),
[research judgment](./tests/research-judgment-cases.md),
[research transfer](./tests/research-transfer-cases.md),
[information discovery](./tests/information-discovery-cases.md), and
[restriction scope and recovery](./tests/restriction-drift-cases.md). The inherited
[information discovery verification record](./tests/information-discovery-results.md)
separates delivery tests from informed synthetic exercises and their limits.
The [restriction scope verification](./tests/restriction-drift-results.md) retains
the source review and fresh-context samples separately from distribution checks.
These cases test decision behavior; they do not prove objective improvement in a
live campaign. The inherited [feedback verification](./tests/feedback-value-results.md)
retains decision-source delivery checks and executor observations. The
[alignment cases](./tests/audit-alignment-cases.md) and
[alignment verification](./tests/audit-alignment-results.md) distinguish selected
source judgment, owner adoption and actual consumer behavior. These inherited

The inherited [engineering verification](./tests/engineering-knowledge-results.md)
and [professional judgment verification](./tests/professional-judgment-results.md)

They are separate from mechanical checks performed on this distribution.

The [professional capability cases](./tests/professional-capability-cases.md)

The distributed `decision-policy.md` links to the repository's `skills/` tree.
When copying the harness into a consuming project, update those relative links
to the actual installed Skill directory, such as `../../.agents/skills/` or
`../../.claude/skills/`. Keep the references relative to the policy file.

## Build and test

Rust 1.89 or later is required.

```sh
cargo build --locked --release \
  --manifest-path tools/workflow-harness/Cargo.toml \
  --bin workflow-harness \
  --bin workflow-codex-hook

cargo test --locked \
  --manifest-path tools/workflow-harness/Cargo.toml \
  -- --test-threads=1
```

The project Hook calls `run-codex-hook`, which selects the release binary first
and then a debug binary. Until one has been built, it exits without changing a
tool decision. Build artifacts remain local and are excluded from Git.

## Host-neutral controlled execution

Start a task with a process that implements the JSON-line transport:

```sh
tools/workflow-harness/target/release/workflow-harness \
  TASK.json NEW_RUN_DIRECTORY --stream-adapter ADAPTER.json
```

The adapter configuration names a process and its literal arguments plus its
actual capabilities: events, controlled continuation, cooperative cancellation,
recovery, fresh context, and isolation. Capability declarations are not proof;
the selected backend must route the covered actions through the boundary.

At an idle boundary, the backend waits for a `continuation` message. A `return`
decision permits settling current work and returning evidence, not starting new
discretionary work. Cancellation begins as pending. Unknown live effects stay
unknown until reconciled, and recovery never converts a persisted intention
into proof that the backend received or completed it.

## Managed subprocess host

This optional execution path owns command admission inside one Session. Its
backend exchanges newline-delimited JSON over pipes; commands are started by
the Harness, not independently by the backend. A model integration must route
every action for which it claims coverage through this protocol. This is an
execution boundary, not a sandbox or an automatic adapter for a desktop Agent.

Use the ordinary task and Session setup, then drive the prepared request:

```sh
workflow-harness host start TASK.json RUN_DIRECTORY
workflow-harness host managed-drive RUN_DIRECTORY < BACKEND.json
```

`BACKEND.json` has `program` (an absolute executable path) and optional `args`.
The backend receives the complete current `Invocation` as its first input line.
It may emit an action and wait for the reply, or return the ordinary response:

```json
{"kind":"action","action_id":"measure-1","command":{"program":"/absolute/tool","args":["argument"]}}
{"kind":"return","response":{"invocation_id":1,"role":"coordinator","decision":"finish","summary":"Supported conclusion","evidence":["/absolute/result.json"]}}
```

The host replies to an action with `action_result`, including the original
invocation, action key, exit code and stdout/stderr paths, or `denied` with a
reason. A repeated key cannot execute twice. Invocation identity comes from the
host's pipe, not a backend claim; an optional mismatching `invocation_id` is
rejected. Diagnostics belong on stderr. A normal return ends this drive; use
the existing owner and `host continue` for subsequent ordinary work.

The host reuses the existing execution record and action checks, including pause,
selected observation points, changed watched outputs and pending challenges.
Backends may send `{"kind":"event","event":{"kind":"usage","total":...}}`
or the existing `progress` and `challenge` event payloads; the host assigns their
invocation and sequence and replies with `recorded`. Missing usage remains
unknown. Backend reports do not certify their own accuracy. Only the host records
stopping and settlement, after reaping the backend and retaining action outcomes.
Selected return conditions refuse further actions; they are not hard operating
system resource limits or permission to interrupt an admitted external effect.

The responsible owner can publish a correction while a backend is running:

```sh
workflow-harness host managed-correct RUN_DIRECTORY < CORRECTION.json
```

```json
{"correction_id":"scope-repair-1","expected_invocation":1,"replacement":{"assignment":"Complete corrected assignment","objective":"Complete corrected objective","constraints":"All still-applicable limits","actual_use":["/absolute/current-task.md"]}}
```

Only `assignment` is required inside `replacement`; omitted fields retain their
values. Use the existing adopted owner sources and current-use checks. This
command is an owner action, not part of the backend protocol or authority to
alter a user's objective. It atomically saves the replacement and retires the
old invocation under the same Session lock used to start commands. The backend
cannot authorize old actions by claiming a newer identity. Queued old actions
are refused, and alternate Session transports cannot take over an enrolled
invocation. All requests on the old pipe share this binding; other Sessions
are outside this controller's scope, including ones using the same source file.

An admitted command finishes with its original identity. Once it settles, the
driver reaps the old backend and installs a complete successor request through
the existing renderer, returning the correction to the Coordinator for adoption.
It requires neither an acknowledgement nor voluntary cooperation from the old
backend. It preserves completed effects, raw backend messages and historical
returns; it does not replay old operations. Writing the input establishes byte
delivery, not that the Agent understood it or made the right decision.

The checkpoint retains correction identity, invocation eligibility, installation
state and action intent/outcome. Repeating exactly the same correction recovers
its recorded successor; changing its body under the same key fails. After a
crash, `host managed-reconcile RUN_DIRECTORY` imports only correlated saved
completion receipts. A missing receipt remains uncertain and blocks dependent
successor installation; it never authorizes replay. An uncertain backend
installation is not retried. Publish a successor through the owner after
reconciling admitted effects, preserving their original receipts.

Saved context is immutable evidence. Admission and current-result acceptance
also check the participating live source bindings. A changed live source must
be reconciled before further dependent use; editing a file alone does not
activate a successor. Arbitrary concurrent filesystem writes are not serialized
by this controller, so this is not protection against mutations after a check.

Coverage excludes backend effects performed outside the pipe, command descendants
that outlive their admitted parent, other Sessions, native desktop tools and
remote hosts without this mediation. The controller cannot revoke effects
already admitted or guarantee external exactly-once execution. Use it only where
the chosen backend obeys that tool-routing contract. Existing adapters and the
configured observational Hook gain no additional coverage merely from this code
being present. Tests in `tests/managed.rs` execute this real host and subprocesses;
they do not establish model quality or live project adoption.

## Use an agent host directly

The host bridge lets the current coordinating agent perform its normal agent
calls while the harness preserves identity and ordering:

```sh
tools/workflow-harness/target/release/workflow-harness \
  host start TASK.json NEW_RUN_DIRECTORY
```

For a host that supports a recoverable correlation identifier before dispatch,
first pass the following object on standard input to
`host prepare-dispatch RUN_DIRECTORY`:

```json
{"invocation_id":1,"call_id":"host-supported-correlation-id"}
```

Then dispatch the emitted request once through that host using the same
correlation. The identifier must actually locate the host call; an invented
label the host cannot retrieve provides no lost-response recovery. Do not
require a host-generated identifier before the host makes it available. If no
supported pre-dispatch association exists, use the original host records and
the legacy bridge below, retaining its narrower coverage.

After acceptance, or after finding the original call during recovery, pass this
object to `host reconcile-dispatch RUN_DIRECTORY`:

```json
{"invocation_id":1,"call_id":"host-supported-correlation-id","outcome":{"status":"accepted","backend_handle":"actual-host-agent-handle"}}
```

The same operation accepts `outcome` with `status: "unknown"` and an `evidence`
explanation when lookup is inconclusive, or `status: "not_started"` and evidence
when the host reliably confirms that exact attempt never started. Generic error
text or an absent handle is insufficient. Accepted and confirmed non-started
outcomes cannot be overwritten by contradictory reports. `host status` exposes
the original association and retained history after a cold open.

Only after confirmed non-start and a grounded recovery opportunity, pass the
old invocation number as a JSON integer to
`host retry-not-started RUN_DIRECTORY`. It emits a new invocation for the same
work, retains the failed attempt, and does not itself dispatch. Use the emitted
role and request; do not reuse the old invocation or call identifier. Unknown,
unsupported and stale recovery responses cannot authorize this transition.
This is an existing-owner recovery operation, not an approval stage.

In the legacy bridge, the coordinator sends the emitted prompt to the emitted
role, then records the actual returned handle:

```json
{"invocation_id":1,"backend_handle":"actual-host-agent-handle"}
```

Pass that object to `host bind RUN_DIRECTORY`. When the agent returns, pass its
handle and structured response to `host return RUN_DIRECTORY`. Use `host status`
to recover an existing pending invocation and `host continue` only when no
invocation remains pending. Never use a new run directory to bypass unresolved
effects or an uncertain dispatch.

For a controlled stream adapter, pass its existing adapter configuration on
standard input to `host recover RUN_DIRECTORY`. This reports structured recovery
state without dispatching; after reliable non-start and an availability change,
use `host retry-not-started`, then `host drive` with the same configuration.
The library equivalents are `Session::recover_backend` followed, when
appropriate, by `Session::retry_not_started`. A reliable non-start receipt uses
`{"status":"not_started_confirmed","invocation_id":1,"evidence":"backend evidence"}`.
The old uncorrelated `not_started` receipt remains readable but cannot authorize
retry. Local stream-process creation failure records a correlated receipt;
disconnection after startup remains uncertain. A successfully accepted invoke
or execution event cannot subsequently be erased by a non-start claim. These
checks correlate evidence; they cannot establish that an adapter's assertion is
true or release resources owned by the host.

For a participating current-use correction, validate the owner and affected
sources with `frontier_references.py check-current-use`, then pass that JSON
report to `host current-use-adopt`. The coordinator identifies the saved task
and dependency paths consumed by the next Worker request in `actual_use`. If an
affected request is queued but has not started, `host current-use-replace` emits
a corrected replacement and may accept the replacement's actual-use paths.
Before external dispatch, `host current-use-check` compares the actual request,
scope, and retained bytes with the binding. These operations preserve the
owner's judgment; they do not create a new approval or infer correctness from
hashes.

When that owner correction changes a restriction in the task header, use
`host current-use-correct RUN_DIRECTORY CORRECTION.json`. The JSON object
requires `assignment`; optional `objective`, `constraints`, and `actual_use`
replace those values, while omission preserves them. Supply each changed text
field in full, retaining applicable limits. The library equivalent is
`Session::replace_queued_work_with_correction`. This updates only unstarted
queued work and persists the corrected header with its assignment; it does not
change execution controls or grant a Worker permission to revise constraints.
The older `current-use-replace` command changes only assignment/use and keeps
the header. Under enforced decision handling, a changed header returns a
Coordinator request for adoption through the existing judgment or explicit
judgment-reuse path before Worker dispatch. Dispatch the returned role, not an
assumed Worker. An unchanged header adds no such owner turn. Inspect the
complete emitted request before dispatch, including any
source excerpts that could omit later qualifications; use `context-read` for
the necessary exact original. Neither command certifies semantic authority.
Already pending or running sessions are not migrated by rebuilding the binary.

This path orders participating calls but does not own the host's agent API and
cannot safely stop arbitrary work already running outside its boundary.

## Optional consequential-decision bridge

The bridge in [decision-bridge.md](decision-bridge.md) can attach one bounded,
independent check to a materially new or revised investment. It is opt-in and
starts in observation mode. Ordinary implementation progress does not create
another review, and a retained judgment can be reused when its scope still
applies. The detailed command contract and recovery rules live in that file.

The bridge does not prove better optimization decisions. Evaluate it by whether
it changes consequential work or reduces uncertainty at acceptable cost, not by
the number of checks or receipts it creates.

The current bridge also binds an adopted judgment to its objective, evidence,
selected consequence, and actual outgoing assignment. Exact ordinary progress
may reuse that binding. A changed assignment, route-ending restriction, or
consequential terminal result must return to the existing owner; an old accepted
reference or unchanged route label is not enough. Bounded completion and a real
mandatory stop remain immediate owner declarations and do not become extra model
calls. These checks establish recorded correspondence only. They do not prove
that an owner's equivalence explanation is semantically correct.

## Codex Hook

The repository includes [`.codex/hooks.json`](../../.codex/hooks.json). Codex
loads this project layer only after the repository is trusted, and changes to
the definition require normal Hook review. Inspect the active definition with
`/hooks` in Codex.

The Hook resolves the repository with `git rev-parse --show-toplevel`; it does
not contain a machine-specific checkout path. It observes only a root Codex
session that has an explicit pointer at:

```text
.frontier/hook-context/<session-id>.json
```

The Frontier helper creates or refreshes that pointer when the coordinator runs
`frontier_references.py adopt-work` for saved current work. Without a valid
pointer, the Hook emits no workflow context and never blocks ordinary work.

Configured events are deliberately narrow:

- `SessionStart` restores concise adopted-work context after startup, resume,
  or compaction;
- `PreToolUse` refreshes that context and records the exact input for supported
  agent dispatch calls; and
- `PostToolUse` correlates the response for those same dispatch calls.

The observer does not inspect arbitrary shell text, call a model, grant
permission, deny tools, rewrite calls, resume paused work, or continue a session
automatically. A successful dispatch receipt is not worker completion or
semantic acceptance. Missing or malformed optional state degrades observation
coverage without creating a new authority boundary.

Do not copy this Hook into another agent's configuration format. For Claude Code,
deploy `AGENTS.md` or its documented `CLAUDE.md` import adapter; those instruction
files are separate from Codex Hook execution.

## Scoped worker adapter

The same binary also retains an explicitly bound worker mode:

```text
workflow-codex-hook WORKSPACE SESSION_ID AGENT_ID RUN_DIRECTORY
```

It applies only to one verified worker, session, repository, pending invocation,
and native turn. Enable it with `run/hook-enabled.json` containing JSON `true`.
Disable it before removing a cached host definition. The adapter can return a
Codex `PreToolUse` denial when the shared session says the worker must return to
its coordinator; unrelated parent, sibling, repository, and tool activity stays
outside that binding.

Use this mode only after verifying the host's actual session and agent identity.
An instruction or declaration is not evidence that native callbacks cover the
intended action.
