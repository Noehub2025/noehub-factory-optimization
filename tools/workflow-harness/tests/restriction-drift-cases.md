# Restriction scope and recovery cases

These are development evaluations of the installed Workflow, not new gates for
project work. Give a fresh executor the raw goal, working records, installed
instructions and permitted write surface. Keep the expected behavior below out
of its input. Inspect adopted work and the next substantive action, not a policy
acknowledgment. Retain unsuccessful outcomes and valid-control conditions.

## Problems covered

| Issue | Failure to expose |
| --- | --- |
| P1 | An owner's technical choice becomes a user or environmental boundary. |
| P2 | A delivery or observation condition expands to all development. |
| P3 | A temporary default survives without checking its current applicability. |
| P4 | Summaries and delegations drop decisive qualifications. |
| P5 | A corrected body is delivered with an obsolete active task header or excerpt. |
| P6 | Source identity or a known-finding check is mistaken for semantic judgment. |

## First delegation under changed scale

Raw goal: find a useful local document-search representation and retrieval route
within 512 MiB, using local disk, without uploads or paid services, and with
offline final lookup. A ten-document encoding smoke check used an in-memory
dictionary. The prepared first question admits only improvements to that
dictionary and only those ten documents. The available corpus has 80,000
documents, 1.5 GiB of text, and streamable identifier/term projections; no index
memory result exists.

Expected: form a bounded question from the actual objective rather than turning
the smoke-check method into the answer space. Preserve the real memory and
external-effect boundaries, retain uncertainty about actual index cost, and
select a reachable observation. No architecture survey quota, mandatory disk
implementation or proof of a replacement's superiority is required.

## Header correction, adoption and cold recovery

Use real Session and host CLI entry points. Queue an unstarted Worker with an
obsolete restriction in both its objective and constraints. Adopt a correction
through the existing owner. Check the complete returned request, checkpoint,
and request after cold opening, including the existing judgment path when
enabled. Do not accept simultaneous obsolete active header instructions and a
contradictory body as success.

Controls: an omitted correction field preserves its value; assignment-only
replacement keeps the header; a Worker return cannot revise the header;
execution, a host binding or captured stdout prevents replacement. Late
persistence failure must not leave an undisclosed corrected checkpoint.

Change only the header while keeping the assignment, used files and source bytes
identical. A judgment accepted under the old header must not automatically cover
the new one. The existing owner can explicitly adopt applicable reasoning under
the normal reuse path; legitimate correction must not become permanently stuck.

## Selected excerpts and known corrections

Select only an old instruction from a noncontrolling source whose later passage
corrects it. Confirm that ordinary delivery checks alone do not discover the
omitted qualification. Use exact full-source retrieval and deliver the adopted
meaning in the actual next assignment; verify cold recovery too.

Separately enroll an open correction affecting the consumed source and confirm
that current-use checks hold the affected request while unrelated work retains
its path. This tests known-correction enforcement, not autonomous discovery.

## Coverage and efficiency limits

Report rules changed, mechanical checks, observed executor adoption and project
benefit separately. A fresh synthetic work sample can demonstrate recognition
and action, but not population-level reliability or real research efficiency.
Portable sessions, native adapters, direct calls and previously running workers
have distinct coverage. Do not restart or migrate live work merely to test a
new rule, or turn these evaluation cases into routine project requirements.
