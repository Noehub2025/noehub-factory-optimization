# Evaluation design repair

This is an inherited source-verification record. The source executor samples
and independent reviews were not rerun during distribution migration.
Distribution checks are reported separately; consuming-project business state
and local evidence workspaces are outside this portable bundle.

Date: 2026-10-08. Scope: the installed Workflow's evaluation preparation,
reuse, independent sampling and adoption. The repair changes shared Skill
guidance and its Harness documentation, not the Harness runtime, business
algorithms, live measurement definitions or external operations.

## Problems and receiving paths

| Problem | Maintained correction | Endpoint to inspect |
| --- | --- | --- |
| P1. Work answers supplied questions but misses evaluation needs | Professional preparation starts from the objective, mechanism, conditions and intended decisions, including ordinary Batch work | Actual observation arrangement and next recommendation |
| P2. Mechanism knowledge substitutes for evaluation knowledge | Reuse depends on the question and use actually supported | Sampling, feedback and interpretation have applicable grounds |
| P3. The diagnostic fast path skips preparation | The original Batch and measurement-work entries now check actual and cumulative use before classifying it as unchanged | Ordinary and direct work can use sufficient grounds without a formal design task |
| P4. Early scope, reused data and old tools become permanent | Check cumulative use; distinguish historical reproduction from a newly adopted scope | Current inputs, configuration, consumer and output follow the adopted definition |
| P5. Shared premises or previous approval prevent scrutiny | A selected independent sample can include previously passed premises and omitted needs; formal Phase A may obtain independent knowledge | The checker can choose the premise and evidence without reading the old protocol early |
| P6. Useful aggregate feedback postpones research capability indefinitely | Assess information needs of the continuing commitment at existing investment points; dispose of a due deferral even after favorable feedback | Actual next work or supported decision not to build the capability |
| P7. Rules change while receiving work retains the old premise | Trace assignment and actual inputs through adoption and next use, including rejected or deferred findings | Real follow-up, recovery or terminal disposition, not a delivered reminder |
| P8. Repair creates routine overhead | Reuse sufficient grounds in the same turn; retain existing owners and limited audits | Unchanged valid use continues without new research or review |

## Verification method

The incremental baseline is a disposable source-verification workspace; Git HEAD
also contains unrelated earlier work. The source diff, mechanical results and
isolated evidence are in a disposable source-verification workspace. These temporary
paths are local verification artifacts, not installed runtime dependencies.

The author queried Context7's OpenAI Agents documentation on
[handoff boundaries](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md)
and [guardrail coverage](https://github.com/openai/openai-agents-python/blob/main/docs/guardrails.md).
Those references informed the distinction between delivered context and actual
coverage; this repair adds no SDK dependency or claim of universal enforcement.

The installed `skill-creator` guidance was used. Initial independent review of
nine source files found no required static correction. A subsequent entry-path
check found that the framing Skill still excluded unchanged execution before
checking actual use; its original sentence was corrected. Independent review
then found that a Coordinator could use an existing runner through
`batch-current.md` without reading the measurement preparation entry until result
adoption. That entry now routes to preparation before classification or reuse.
Both files were added to the pre-change baseline before editing. A later behavior
sample exposed a remaining discoverability problem: the executor did not follow
that link before its first calculation. The Coordinator Skill now directly routes
measurement to professional preparation before selecting the definition or
invoking the evaluator, and the Batch route was moved to the reference's entry.
The source increment is twelve files, each saved before editing. These are real
review and execution findings, not a claim that the first implementation already
covered every entry.

Mechanical validation passed for the changed Skill entrypoints with the
installed `quick_validate.py`. The existing bundle validator reported
`bundle_ready: true`, `legacy_compatibility_ready: true` and no findings.
No runtime source changed in this repair, so existing unrelated runtime tests
are not presented as its behavioral evidence.

## Bounded behavior samples

Fresh agents receive only ordinary task requests and raw working material.
Neither receives this report, the intended failure, the source diff or earlier
audit conclusions. The fixture names and task titles do not name the intended
defect. No evaluation-method answer or professional reading list is supplied;
normal public read-only evidence access remains available. Both use installed
Workflow guidance. Local task files stand in for Batch state, so these samples
exercise Skill-guided decisions and concrete consumers, not the native Batch
API or Codex Hook.

- `run-a`: complete a first local controller comparison from operating notes,
  request logs and a prototype evaluator, then send the completed report and
  recommendation to a local file consumer. Historical reproduction is retained.
  Inspect the chosen evidence, actual scope, calculation and next recommendation.
- `run-b`: recover two local arrangements, decide the next supported action,
  and send those dispositions to a local consumer. One uses repeated development
  results in a proposed broader route decision; the other retains a covered
  regression use. Inspect cumulative-use reasoning and unnecessary extra work.
- `run-c`: a Coordinator resumes measurement through the existing runner without
  a worker or implementation assignment, starting from the Frontier Skill. The
  raw fixture matches the initial controller comparison, but this agent sees
  neither `run-a` nor its results. Inspect preparation before execution through
  the newly connected entry.
- `run-d`: repeat the Coordinator-entry task in another fresh context after the
  discoverability correction, using the untouched original inputs and request.

## Live adoption boundary

The source checkpoint located the existing owner's next official-result adoption
and research-allocation decision as an affected receiving point. It was a file
snapshot, not a fresh provider receipt, and the source repair changed neither the
live assignment nor its external operation. That snapshot is not current state
for a consuming project and is not reproduced in this distribution.

At actual use, the existing owner should match evaluation grounds to the intended
and cumulative decisions and dispose of due deferred questions. Useful aggregate
feedback and information needed for continuing research remain distinct. The
repair prescribes no new panel, automatic restart or invalidation of historical
results. No business-chat message or owner adoption was established by the source
repair. Source deployment and isolated samples do not prove live uptake, research
efficiency or objective improvement.
