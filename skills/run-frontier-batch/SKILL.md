# Run Frontier Batch

Execute one authorized B packet. The acknowledgment invocation returns only the immutable acknowledgment and performs no work or spend. One or more sequential execution invocations may then continue from the same Coordinator-owned execution-start until the B publishes one result. Professional implementation-design authoring belongs to `design-implementation`; a design or prototype B obtains only the executable evidence named by its packet. Do not decide what the campaign retains, promotes, or claims.

## Validate the assignment

1. Require the packet's exact `decision_root`, immutable packet identity, exact authority, project content roots, and assigned paths. Verify the typed project provenance chain, apply the [Batch Interface state machine](../frontier-optimization/references/batch-interface.md#dispatch-state-machine), and reproduce the frozen structural preflight before writing anything. New packets must not contain workflow source, Skill, validator implementation, release, or module roots. Historical semantic contracts already restricted to audit remain audit-only. This restriction does not apply to valid current chains merely because their storage adapter is `portable-bundle/1`.
   The installed workflow may change between acknowledgment, execution, and recovery. That change never changes the packet, project identity, authority, or result path; apply the current execution method only to the unchanged project facts.
2. On the acknowledgment invocation, resolve the exact immutable authority named by the packet: `ENTRY_READY` adoption or direct spend-readiness, later `REPLAN_READY` and learning gates, and every applicable design or implementation review. A missing, conditional, mismatched, or repaired authority chain returns `BLOCKED` with zero work and spend. On the execution invocation, require the applicable current-state and freshness checks; a stale or expired authority blocks execution without changing the acknowledgment.
3. Recheck path ownership. Worker-forbidden paths restrict this worker; execution-frozen inputs restrict every actor only after execution start. Reject any overlap among worker writes, forbidden paths, frozen inputs, and Coordinator outputs according to Batch Interface.
4. When `changes_executable_candidate: true`, read [candidate lifecycle](../frontier-optimization/references/candidate-lifecycle.md). When B cites W, verify the currently authorized design inputs, dependency-complete `delivery_scope`, required concerns, traceability, and source and output paths. For an explicitly delegated design revision, use the revised design proven in the current execution snapshot; do not require it to retain the original design identity. Load only matching `Read when` contracts. Keep assignment, mutable work breakdown, internal paths, runtime status, and current authorization outside Design.
5. Accept campaign-cycle work supported by the packet and available tools. Mixed work follows each component's actual authority and effect limits. External, paid, human, or physical operations are never implicit working feedback: require an explicit original authorization naming the exact target, action, affected scope, cumulative limits, and stop conditions, plus an available tool and containment that enforce those bounds. Otherwise return the exact capability or authority blocker for that operation. Do not build a universal executor or infer permission from the work-kind label. Unsafe parallel work remains blocked; closeout and claim adoption remain Coordinator work.
6. On the acknowledgment invocation, run static consequence verification with empty live facts and `checked_at: null`, write the Batch Interface acknowledgment with the exact `decision_root` and recomputed packet-preflight, authorization-adoption, and adoption-validation identities, then return without work or spend. On the execution invocation, require their structured file bindings and a live-verified execution-start record with the same decision root plus `worker_may_start: yes` before setting `started_at`. A legacy execution-start is audit-only and grants no work authority. For user-owned authorization, require the derived `frontier-post-adoption-state/1` receipt and let the bound baseline tool verify the exact reviewed live post-state while rejecting partial or extra drift. When a current record also contains `frontier-lifecycle-transition/1`, verify its single UTC instant, derived date, exact three-field receipt, pre/post identities, and matching frozen live bytes through the same tool.

Validation is complete only when this invocation has written one durable acknowledgment and returned, or has verified a valid execution start and may enter the packet's work, or has returned a durable blocker with truthful zero or known spend. Use `waiting_for_input` only under a complete human-input contract.

## Execute within the packet

Set `started_at` only after the execution-start record and its required starting inputs pass. Apply [Provenance, Git, and retained artifacts](../frontier-optimization/references/provenance-and-identity.md) for Git references, scoped input checks, and working changes. Start with the smallest useful checkpoint and protect the preparation limit and follow-up reserve. Check actual declared inputs at consumption and current action facts at their consequence. Normal edits to working material or unrelated files do not invalidate retained inputs.

Apply [Boundary-preserving continuation](../frontier-optimization/references/batch-interface.md#boundary-preserving-continuation) before deciding whether to continue, request implementation review, or publish a terminal result. Preserve formal closing attempts, cumulative effects, and necessary failure logs. Keep working feedback inside the same B without lifecycle records; publish a terminal result when a substantive boundary changes or continuation can no longer satisfy the same B.

For W-backed work, satisfy every obligation in `delivery_scope` and the complete integration check. Maintain a mutable work breakdown inside the assigned workspace; add, remove, merge, replace, or reorder its steps as evidence develops. Append bounded observations only to assigned Milestones and progress or Decisions and discoveries regions. Record the current blocker, remaining completion gap, and next action with its switching condition before returning between invocations. Do not edit W Purpose, Scope, Design brief, Design map, Human input contracts, Delivery map, Validation, Definition of done, or any concern contract.

For candidate code, verify the assigned inputs, output scope, and engineering check plan. Before a formal closing check, verify selected units and consequential effects against the authorized limits and existing containment evidence. Do not enumerate every harmless internal operation or demand a separate proof for each. A demonstrated boundary violation or unresolved consequential effect blocks that check; unfamiliar syntax or hypothetical risk alone does not. Engineering fixtures are not performance evidence. Reuse unaffected evidence only when its actual dependencies remain valid, retaining necessary integration checks.

Build the complete observable realization through working feedback under the canonical Batch Interface seam. Local editing, compiling, linting, focused checks, debugging, temporary materialization, and inventory preparation remain worker-owned and unrecorded while they stay reversible, local, and inside the packet envelope. When the realization is ready, derive its transient inventory and stage it into a fresh exclusive runtime. The formal attempt starts with the first frozen engineering check. If the controlling parent instead charges an earlier identity or exposure event, preserve that recorded ordering and stop using the prepublication repair path at that event. Formal measurement, sealed evidence, selection-producing evaluation, human judgment, remote or paid work, physical action, publication, and other material external effects are excluded from working feedback.

For a formal closing check or another consequence-bearing action, stage only validated inventory members into the exclusive runtime. For Python, also use `-B` or `PYTHONDONTWRITEBYTECODE=1`. Never load formal code from the canonical candidate root. Verify the actual selected inputs at the formal consumption boundary and again if those inputs may have changed. Reuse an unchanged retained version rather than rehashing the whole working directory after each command. Working feedback has no formal evidence consequence and cannot use a formal, sealed, remote, paid, or otherwise limited channel.

When the complete realization passes its formal closing attempt, freeze its exact transient inventory, cumulative formal-attempt reports, design or direct target, execution-start, and closed review collection for fresh-context implementation review. A positive review permits only publication of those exact bytes. Apply Batch Interface's continuation rule to fidelity findings, design revisions, and failed retries; do not create a second stop rule here.

After the final positive review, publish the official inventory atomically from byte-identical reviewed bytes. Use `already-present-identical` to recover publication of the same recorded event under [Charging and publication](../frontier-optimization/references/batch-interface.md#charging-and-publication); it proves content equality, not a free new proposal. Bind completed engineering evidence and cumulative effects, then write the final manifest and validate it before the result. Preserve changed official bytes as evidence; never silently repair published output. Set `materialization_state: materialized-stopped`, carry the unchanged `IMPLEMENTATION_READY`, and keep integration `not-authorized` and `experiment_identity: null`. Without an explicitly authorized working diagnostic target, performance remains `not-authorized` and `results: []`; with one, preserve its bounded observations under Batch Interface without promoting them to candidate strength evidence.

For an authorized diagnostic of working material, follow [Bounded observations before publication](../frontier-optimization/references/batch-interface.md#bounded-observations-before-publication). Do not wait for complete delivery or create a new experiment B merely to perform that observation. Preserve cumulative consumption and actual evidence; ordinary local debugging stays unrecorded.

For a Slot H evaluation B, require `work_kind: experiment`, `changes_executable_candidate: false`, and the canonical nested `evaluation_target` from Batch Interface. The target binds one complete immutable candidate root and manifest, unchanged adopted `IMPLEMENTATION_READY`, the Slot H contract, and a precomputed experiment identity covering the evaluator, data, controls, protocol, environment, budget, campaign generation, and result paths. Treat `evaluation_target.experiment` as the only experiment-identity source; prose fields refer to it without copying the identity. Recompute both the complete candidate package and the experiment identity before acknowledgment. Stage the candidate into an exclusive runtime copy before any load and apply the same Python bytecode suppression. In post-closeout recovery, also require the packet's frozen finding-free candidate-recovery preflight, recovery V, X, inherited Budget, and candidate identity to match the adopted Entry and implementation review. Do not change candidate bytes, evaluator semantics, comparison controls, or measurement inputs. Run only the assigned measurement and comparison-validity checks, preserve raw results, and copy the complete packet `evaluation_target` exactly into the result. Do not add flat experiment-binding aliases, create E, retain or promote the candidate, or choose the next B.

For `evaluation_target.mode: routine-local`, require the Coordinator's released execution node and exact consumed slot before loading the candidate. Copy the target and its structured `evidence_scope` unchanged. Run only the fixed single-use schedule and local-resource ceiling. Report B evidence only; do not create E, rerun calibration, add samples, satisfy formal Slot H, integrate, select an incumbent, promote, submit, publish, take an external or paid action, state a strength claim, or choose or authorize another B.

For a result-publication recovery B, do not rerun a completed measurement. Require the packet to bind the source B, each raw artifact and identity, unchanged measurement semantics, zero reruns, and a prohibition on new measurement execution. Recompute every bound source identity before acknowledgment, then recompute only the authorized derived summary. Report `actual_spend: 0 new measurement spend` and the exact zero-valued `evidence_reuse_accounting` mapping from Batch Interface, and publish under the new B identity. A missing byte, identity mismatch, changed interpretation, or contradictory accounting is `BLOCKED`; it is not permission to sample again.

If implementation exposes a shared-interface or other contract-bearing change, write only a discovery with evidence, affected contract, and consequence. Do not edit the contract. The Coordinator applies the realization-revision rule in Batch Interface: revise and review Design and Entry under the same B when its envelope is unchanged; ask again or end the B only when that envelope changes.

A design B answers only its named executable evidence question; it does not author or adopt W professional content. A non-code prototype writes isolated evidence and cannot be measured, integrated, promoted, or relabeled as a candidate. If actual work changes executable code, report the scope deviation and do not bypass the code gates.

For human input, validate that the packet names the exact request, schema, provenance, quality and legality checks, confidentiality handling, response path, accept or reject conditions, and resume event. When no response exists, write the request and return `waiting_for_input`. When it exists, preserve its bytes and metadata, run only assigned checks, and report `received-unvalidated`, `accepted-as-evidence`, or `rejected`. Never turn supplied data into a technical conclusion, E, or user value choice; route an actual preference or authorization through V.

Apply legality, measurement, and comparison checks only when the packet authorizes that phase. Report observed versus expected evidence and decision-relevant surprises without selecting a follow-up. A diagnostic B must run the assigned smallest distinguishing check only; a focused-research B must not expand into a route-landscape refresh unless its packet authorizes that scope.

Write only the assigned acknowledgment, artifacts, permitted W progress or discoveries, package inventory and final candidate manifest when applicable, result-validation artifact, and exactly one result packet. Between execution invocations, keep working material in assigned paths and complete the ordinary progress note; do not create an inventory or attempt report for working feedback. Never write the Coordinator-owned packet preflight, execution-baseline snapshot, or execution-start record. Produce the result through [Batch Interface: Batch result](../frontier-optimization/references/batch-interface.md#batch-result), including draft and byte-identical frozen validation before atomic publication. Account for the execution baseline, every formal closing attempt, output, check, effect occurrence, spend item, deviation that affects formal evidence, input state, and recovery point. A recovery point cites the retained Git version and required external artifacts, so later working changes do not obscure the reviewed realization.

Return every simple non-code outcome truthfully: `completed`, `interrupted`, `failed`, `blocked`, or `waiting_for_input`. Use `actual_spend: unknown` when accounting cannot establish an amount; never replace unknown spend with zero. Worker output is evidence only and never creates E or adopts a campaign result.

For every formal closing attempt, write one combined `frontier-engineering-check-report/1` that binds the snapshot, ordered frozen check IDs and command digests, exit status, and log digests. Derive cumulative effects from the frozen `effect_costs`; do not self-report lower values. A complete all-pass attempt cannot be relabeled as failure. If review later rejects it, preserve that pass with the nonpositive review handoff before another all-pass realization replaces it.

Execution is complete only when every `delivery_scope` obligation, output, check, review, effect, and spend consequence is accounted for; the final published bytes equal the positively reviewed inventory; the existing accounting owner has reconciled actual events under Batch Interface or recorded the exact reconciliation blocker; the immutable result passed frozen validation; and the recovery point lets a fresh Coordinator audit or resume without conversation history.

Do not edit parents, F1-F8, ledger records, designer-owned Design brief or concern bodies, Coordinator-owned W sections or mechanical bindings, or review artifacts. Do not change the packet, move budget, integrate or promote a candidate, stop the campaign, or publish a claim.
