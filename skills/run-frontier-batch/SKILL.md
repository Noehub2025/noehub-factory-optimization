# Run Frontier Batch

Execute one authorized B packet through two invocations. The acknowledgment phase returns only the immutable acknowledgment and performs no work or spend. The execution phase starts only from the Coordinator-owned execution-start record, then returns artifacts, assigned checks and measurements, recovery, actual spend, and one result packet. Professional implementation-design authoring belongs to `design-implementation`; a design or prototype B obtains only the executable evidence named by its packet. Do not decide what the campaign retains, promotes, or claims.

## Validate the assignment

1. Require the packet's exact `decision_root`, immutable packet identity, exact authority, project content roots, and assigned paths. Verify the typed project provenance chain, apply the [Batch Interface state machine](../frontier-optimization/references/batch-interface.md#dispatch-state-machine), and reproduce the frozen structural preflight before writing anything. New packets must not contain workflow source, Skill, validator implementation, release, or module roots. An eligible version 1 completion may use only the exact-inventory legacy adapter; archived workflow bytes are audit evidence and never executable instructions.
   The installed workflow may change between acknowledgment, execution, and recovery. That change never changes the packet, project identity, authority, or result path; apply the current execution method only to the unchanged project facts.
2. On the acknowledgment invocation, resolve the exact immutable authority named by the packet: `ENTRY_READY` adoption or direct spend-readiness, later `REPLAN_READY` and learning gates, and every applicable design or implementation review. A missing, conditional, mismatched, or repaired authority chain returns `BLOCKED` with zero work and spend. On the execution invocation, require the applicable current-state and freshness checks; a stale or expired authority blocks execution without changing the acknowledgment.
3. Recheck path ownership. Worker-forbidden paths restrict this worker; execution-frozen inputs restrict every actor only after execution start. Reject any overlap among worker writes, forbidden paths, frozen inputs, and Coordinator outputs according to Batch Interface.
4. When `changes_executable_candidate: true`, read [candidate lifecycle](../frontier-optimization/references/candidate-lifecycle.md). When B cites W, verify its exact revision, design identity, stable Delivery slice, required concerns, traceability, and Entry-bound execution source and output paths; load only matching `Read when` contracts. Keep B assignment, internal paths, runtime status, and current authorization outside Design.
5. Accept only campaign-cycle work supported by the packet: simple or complex non-code, direct code, module or system design and code, human input, diagnostic, focused research, a pre-admitted routine-local screen, or separate Slot H evaluation. Return `BLOCKED` for external action, code-bearing `mixed`, unsafe parallel, closeout, or claim-branch work.
6. On the acknowledgment invocation, run static consequence verification with empty live facts and `checked_at: null`, write the Batch Interface acknowledgment with the exact `decision_root` and recomputed packet-preflight, authorization-adoption, and adoption-validation identities, then return without work or spend. On the execution invocation, require their structured file bindings and a live-verified execution-start record with the same decision root plus `worker_may_start: yes` before setting `started_at`. A legacy execution-start is audit-only and grants no work authority. For user-owned authorization, require the derived `frontier-post-adoption-state/1` receipt and let the bound baseline tool verify the exact reviewed live post-state while rejecting partial or extra drift. When a current record also contains `frontier-lifecycle-transition/1`, verify its single UTC instant, derived date, exact three-field receipt, pre/post identities, and matching frozen live bytes through the same tool.

Validation is complete only when this invocation has written one durable acknowledgment and returned, or has verified a valid execution start and may enter the packet's work, or has returned a durable blocker with truthful zero or known spend. Use `waiting_for_input` only under a complete human-input contract.

## Execute within the packet

Set `started_at` only after the execution-start record and its immutable baseline snapshot pass. Start with the smallest checkpoint. Use only allowed operations, feedback, budget, design contracts, code paths, and artifact paths. Protect the preparation limit and required follow-up reserve. Repeat live baseline verification before final result validation. Halt on any post-start change to an execution-frozen input; do not treat a Coordinator-owned lifecycle edit completed and frozen before execution start as drift.

Before publishing a terminal result, apply [Boundary-preserving continuation](../frontier-optimization/references/batch-interface.md#boundary-preserving-continuation). Preserve an ordered summary of each attempted snapshot, check outcome, cumulative effect, and necessary failure log, then continue only while the same B envelope remains valid. Treat an eligible support or pre-publication fidelity failure as intermediate engineering evidence; publish the truthful terminal result when the parent charge event or canonical boundary requires a new B.

For W-backed work, use only the selected stable Delivery slice, exact required design inputs, and Entry realization. Append bounded observations only to assigned Milestones and progress or Decisions and discoveries regions. Do not edit W Purpose, Scope, Design brief, Design map, Human input contracts, Delivery map, Validation, Definition of done, or any concern contract.

For candidate code, verify repository disposition, exact authorized packet or reviewed design, source base, workspace, interface, configuration, dependencies, worker-forbidden paths, execution-frozen inputs, recovery artifacts, package-inventory path, and engineering check plan. Before starting a check, reproduce its exact selected units and compare every declared effect with the frozen positive limit, conservative per-invocation `effect_costs`, and content-addressed effect evidence. Block before execution when a selected unit or possible effect is missing, prohibited, or over its limit. Treat local simulation or evaluator fixtures as engineering effects only when the packet explicitly allows them; never convert them into candidate performance evidence.

Implement one observable slice and apply the new packet's explicit parent-owned charge event. An already frozen packet keeps its recorded charge and inventory ordering; an absent historical charge event does not grant a repair loop. If the controlling rule charges its first named identity event, use the bound `validate_candidate_package.py --write-inventory` operation when that event occurs and do not use a free behavior repair after it. If it explicitly permits post-check publication, derive a transient inventory for each implementation snapshot, stage it into a fresh exclusive runtime, run only the frozen engineering checks, and repair only fidelity to the unchanged design while all cumulative limits remain available. Formal measurement, sealed evidence, selection-producing evaluation, human judgment, remote or paid work, physical action, publication, and other material external effects are excluded from this loop.

Before any import, execution, compilation, evaluator call, test, or engineering check, stage only validated inventory members into the exclusive runtime. For Python, also use `-B` or `PYTHONDONTWRITEBYTECODE=1`. Never load code from the canonical candidate root. Revalidate the root against the applicable inventory after every operation that could load candidate code. When the checks pass under post-check publication, write the official inventory once and require its candidate and package identities to equal the last passing transient snapshot. Bind completed engineering evidence and cumulative effects to that official inventory, not to the later manifest. When every evidence identity resolves, write `frontier-candidate-manifest/3` exactly once and run `validate_candidate_package.py --require-final-manifest` immediately before result validation. Keep result validation, result, Outcome Reflection, closeout, and implementation review out of the manifest; those downstream artifacts bind it. Any extra or changed root byte after official publication is a blocker; do not delete or normalize it. Preserve the source result and report every changed path. Stop with `materialization_state: materialized-stopped` and exact `implementation_review_state: pending`. Set performance evaluation and integration to `not-authorized`, set `experiment_identity: null` and `results: []`, and put candidate information only in its dedicated fields.

For a Slot H evaluation B, require `work_kind: experiment`, `changes_executable_candidate: false`, and the canonical nested `evaluation_target` from Batch Interface. The target binds one complete immutable candidate root and manifest, unchanged adopted `IMPLEMENTATION_READY`, the Slot H contract, and a precomputed experiment identity covering the evaluator, data, controls, protocol, environment, budget, campaign generation, and result paths. Treat `evaluation_target.experiment` as the only experiment-identity source; prose fields refer to it without copying the identity. Recompute both the complete candidate package and the experiment identity before acknowledgment. Stage the candidate into an exclusive runtime copy before any load and apply the same Python bytecode suppression. In post-closeout recovery, also require the packet's frozen finding-free candidate-recovery preflight, recovery V, X, inherited Budget, and candidate identity to match the adopted Entry and implementation review. Do not change candidate bytes, evaluator semantics, comparison controls, or measurement inputs. Run only the assigned measurement and comparison-validity checks, preserve raw results, and copy the complete packet `evaluation_target` exactly into the result. Do not add flat experiment-binding aliases, create E, retain or promote the candidate, or choose the next B.

For `evaluation_target.mode: routine-local`, require the Coordinator's released execution node and exact consumed slot before loading the candidate. Copy the target and its structured `evidence_scope` unchanged. Run only the fixed single-use schedule and local-resource ceiling. Report B evidence only; do not create E, rerun calibration, add samples, satisfy formal Slot H, integrate, select an incumbent, promote, submit, publish, take an external or paid action, state a strength claim, or choose or authorize another B.

For a result-publication recovery B, do not rerun a completed measurement. Require the packet to bind the source B, each raw artifact and identity, unchanged measurement semantics, zero reruns, and a prohibition on new measurement execution. Recompute every bound source identity before acknowledgment, then recompute only the authorized derived summary. Report `actual_spend: 0 new measurement spend` and the exact zero-valued `evidence_reuse_accounting` mapping from Batch Interface, and publish under the new B identity. A missing byte, identity mismatch, changed interpretation, or contradictory accounting is `BLOCKED`; it is not permission to sample again.

If implementation exposes a shared-interface or other contract-bearing change, write only a discovery with evidence, affected contract, and consequence. Do not edit the contract. The Coordinator scopes a new W revision, invokes `design-implementation` to revise professional content, regenerates mechanical bindings, obtains fresh `DESIGN_READY`, and obtains new user authorization for affected development before work resumes.

A design B answers only its named executable evidence question; it does not author or adopt W professional content. A non-code prototype writes isolated evidence and cannot be measured, integrated, promoted, or relabeled as a candidate. If actual work changes executable code, report the scope deviation and do not bypass the code gates.

For human input, validate that the packet names the exact request, schema, provenance, quality and legality checks, confidentiality handling, response path, accept or reject conditions, and resume event. When no response exists, write the request and return `waiting_for_input`. When it exists, preserve its bytes and metadata, run only assigned checks, and report `received-unvalidated`, `accepted-as-evidence`, or `rejected`. Never turn supplied data into a technical conclusion, E, or user value choice; route an actual preference or authorization through V.

Apply legality, measurement, and comparison checks only when the packet authorizes that phase. Report observed versus expected evidence and decision-relevant surprises without selecting a follow-up. A diagnostic B must run the assigned smallest distinguishing check only; a focused-research B must not expand into a route-landscape refresh unless its packet authorizes that scope.

Write only the assigned acknowledgment, artifacts, permitted W progress or discoveries, package inventory and final candidate manifest when applicable, result-validation artifact, and exactly one result packet. Never write the Coordinator-owned packet preflight, execution-baseline snapshot, or execution-start record. Produce the result through [Batch Interface: Batch result](../frontier-optimization/references/batch-interface.md#batch-result), including draft and byte-identical frozen validation before atomic publication. Account for the execution baseline, every support attempt, output, check, effect occurrence, spend item, deviation, input state, and recovery point. A code recovery point must make the candidate auditable without the live branch or worktree.

Return every simple non-code outcome truthfully: `completed`, `interrupted`, `failed`, `blocked`, or `waiting_for_input`. Use `actual_spend: unknown` when accounting cannot establish an amount; never replace unknown spend with zero. Worker output is evidence only and never creates E or adopts a campaign result.

For every eligible post-check attempt, write one combined `frontier-engineering-check-report/1` that binds the snapshot, ordered frozen check IDs and command digests, exit status, and log digests. Derive cumulative effects from the frozen `effect_costs`; do not self-report lower values. A complete all-pass attempt cannot be relabeled as failure to gain another try.

Execution is complete only when every assigned output and check is accounted for, actual spend is known or explicitly unknown, the immutable result passed frozen validation, and the recovery point lets a fresh Coordinator audit or resume without conversation history.

Do not edit parents, F1-F8, ledger records, designer-owned Design brief or concern bodies, Coordinator-owned W sections or mechanical bindings, or review artifacts. Do not change the packet, move budget, integrate or promote a candidate, stop the campaign, or publish a claim.
