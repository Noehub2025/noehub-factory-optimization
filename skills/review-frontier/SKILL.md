# Review Frontier

Review one saved project subject independently and write one R. R is the only current review record; it is not a permission credential or execution identity. Do not repair, research, reselect, ask the user, recommend a Coordinator route, or adopt campaign state.

## Select one review branch

1. Require `review_kind: entry | replan | design | implementation | claims`, one full subject Git commit, explicit repository-relative subject paths, one R handle and output path, applicable parent references, and a completion check. The subject and reference material together must support the selected judgment under [Review input roles and corrections](../frontier-optimization/references/provenance-and-identity.md#review-input-roles-and-corrections).
2. Read the selected saved inputs under that contract. Return a concrete reference error to the Coordinator for correction and continue with applicable work retained. An unresolved required input blocks only its dependent judgment. A later working-copy change does not alter the saved subject.
3. Select the current method through the [review branch registry](../frontier-optimization/references/review-branches.md). Historical inputs establish what happened; current rules govern this judgment. Correct an incompatible kind, scope or completion condition with the Coordinator in the same task, retaining applicable work. Load only the selected method and triggered supporting material.
4. Apply the selected method to the saved project facts. For a correction, inspect the saved diff, changed dependencies, and affected conclusions; do not repeat unaffected work merely because the commit changed.

An installed workflow update never changes the historical subject or verdict. Apply current review rules to the next review without making workflow files, validators, bundle versions, or deployment paths part of the project subject.

Historical review packets, snapshots, content roots, and typed provenance remain readable only when the retained R actually uses them. Do not generate or backfill those fields for current work.

## Preserve review independence

Check source artifacts, not only summaries. Apply [Finding effects](../frontier-optimization/references/finding-effects.md). Cite the affected subject and supporting source content at their saved versions for every block, repair, advisory, and checked positive result. Do not return a positive verdict while a block or repair remains open. Keep advisories separate from readiness, strength, validity, progress, and constraint conclusions. Reuse evidence-backed conclusions for their supported use; a review supplies neither user permission nor an investment decision.

Each finding connects the applicable requirement or evidence gap to the affected next consequence and recovery condition. Apply the current finding effects to distinguish an unusable realization from a non-blocking technical suggestion. Accept any repair satisfying the requirement; a method difference alone is not a defect.

Write only the assigned R artifact with:

- R handle and review kind;
- subject Git commit and paths;
- applicable parent handles;
- verdict and checked conclusions;
- findings and advisories;
- reviewer and assumptions;
- maximum supported consequence; and
- recovery condition when nonpositive.

Do not edit the subject, Campaign, Selection, Batch, Budget, V, E, W, or claims. The Coordinator decides adoption and the next stage. Review completion means the assigned consequential question is answered with evidence and the R artifact passes its ordinary completion check. Return those conclusions for adoption; a later file or stage needs another review only under the branch registry's assurance rule. Reuse checks the prior R's actual subject and assumptions; it does not transfer an attestation or authority node.
